Umami: notes for developers

What Umami is, how it counts visitors without cookies, and when it is (and is not) the right tool. Version details refer to Umami 3.4. For hands-on steps, see the separate tutorial.

On this page 1. Overview 2. Features 3. How it works 4. Counting without cookies 5. What the numbers mean 6. Privacy law and limits 7. Hosting options 8. Comparison 9. Use case 10. Pros and cons 11. What we learned

1. Overview

Umami is an open-source web and product analytics platform released under the MIT licence (Umami Software, n.d.i). A website owner adds one small JavaScript file to their pages; the file reports page views and chosen interactions to an Umami server, which shows them on a dashboard.

Its defining feature is privacy. Umami's tracker works "without cookies, cross-site tracking, or the automatic collection of personal data" (Umami Software, n.d.e). Instead of storing an identifier in the visitor's browser, the server recognises returning visitors with a hash that changes every month (see section 4).

Why it matters Cookie-based analytics usually needs a consent banner, and banner design strongly affects the data collected. Utz et al. (2019) found consent notices on over 60% of popular European websites in their study, and Nouwens et al. (2020) showed that removing the "reject" option from the first page raised consent by 22–23 percentage points. Analytics that depends on consent therefore depends on how the banner is designed.

3. How it works

Umami is a full-stack Next.js application. The same server delivers the tracker script, receives events through an API route and renders the dashboard. Data is stored in PostgreSQL through the Prisma ORM.

  1. The visitor's browser loads the page, including <script defer src=".../script.js" data-website-id="...">.
  2. The tracker sends a small JSON payload to /api/send: page URL and title, referrer, screen size, language and the website ID. In single-page apps it also reports route changes automatically by hooking history.pushState (Umami Software, n.d.i).
  3. The server drops requests whose user agent matches the isbot library and rejects IP addresses listed in the IGNORE_IP setting (Umami Software, n.d.i).
  4. It derives browser, operating system, device and approximate location from the request, computes the session and visit IDs (section 4), and stores the event.
  5. The dashboard reads the same database.

4. Counting visitors without cookies

A cookie lets a site recognise a browser because the browser sends the same stored value back. Umami recognises a visitor by recomputing an identifier on the server from the request itself.

src/app/api/send/route.ts (simplified)
sessionId = uuid( websiteId, ip, userAgent, monthlySalt )
visitId   = uuid( sessionId, hourlySalt )

The function combines its inputs with a one-way hash, so the same inputs always give the same ID but the ID cannot be reversed into an IP address. The salt is an extra value that changes on a schedule: monthly by default for sessions (configurable with SALT_ROTATION) and hourly for visits.

Two consequences follow. First, the IP address is used to compute the hash but is not stored in the session record (Umami Software, n.d.f). Second, after the salt changes, the same person produces a different ID, so activity cannot be linked across rotation periods. A site can deliberately override this with umami.identify(), which assigns its own distinct ID and links sessions; once used, analytics is no longer anonymous by design (Umami Software, n.d.f).

5. What the numbers mean

Because identity comes from a hash rather than a login or cookie, Umami's metrics have precise definitions (Umami Software, n.d.f):

MetricDefinitionWatch out for
VisitorsUnique sessions (unique session IDs)An estimate of people, not a count of identified individuals
VisitsUnique visit IDs; a new visit starts after 30 minutes of inactivityOne visitor can make several visits in a day
ViewsPage views recordedRefreshing a page adds a view
Bounce rateVisits with only one event, divided by visitsA one-page site will show a high bounce rate
Visit durationTime between first and last event, for visits with more than one pageSingle-page visits contribute no time
EventsCustom actions you send, such as a button clickA click is an action, not a completed purchase
Counting errors in both directions The same person on Wi-Fi and then 4G has two IP addresses and appears as two visitors. Two people on the same Wi-Fi with the same browser version can share one ID and appear as one. VPN users are hashed with the VPN server's IP, and their location shows the VPN server's country.

6. Privacy law and limits

Pseudonymous, not anonymous. The European Data Protection Board treats pseudonymised data — data that can no longer identify someone without additional information, such as a hashed identifier — as personal data that remains subject to GDPR (EDPB, 2025). Umami's own FAQ says GDPR compliance "depends on how you configure and use it" (Umami Software, n.d.c).

UK consent rules have changed. Under the Data (Use and Access) Act 2025, the ICO's 2026 guidance allows storage and access technologies used solely for statistical analytics without consent, provided that users receive clear information and a simple, free way to object, results are aggregate, and nothing is used for profiling or advertising (ICO, 2026). For UK sites, Umami's advantage is therefore less about avoiding a banner and more about collecting less data in the first place.

Retention is your job when self-hosting. A self-hosted instance keeps data until you delete it (Umami Software, n.d.c), so the owner must set a retention policy.

Ad blockers. Some blockers block the default script.js and /api/send. Umami can rename both with the TRACKER_SCRIPT_NAME and COLLECT_API_ENDPOINT environment variables (Umami Software, n.d.b). Whether a site should work around a visitor's blocking choice is an ethical question as well as a technical one; the tracker also supports data-do-not-track="true" to respect the browser's Do Not Track setting.

9. Use case: Paisley Christmas Market

Our CW2 scenario is a web app for a new Christmas market in Paisley. Umami could answer the organiser's practical questions without tracking individual shoppers:

Organiser's questionUmami feature
Which stalls attract the most interest?Top pages, plus a "Book stall" event with a stall property
Where do visitors come from?Referrers and UTM-tagged links on posters or social posts
Are visitors mostly on phones?Device breakdown, to justify a mobile-first design
Where do bookings drop off?Funnel: stall page → booking form → booking confirmed (requires tracking the confirmation step)
Can stallholders see results?A share URL for a read-only dashboard

10. Pros and cons

Pros
  • No cookies and no stored IP addresses
  • One script tag; works with plain HTML, React or Next.js
  • Open source: you can read how the numbers are calculated
  • Self-hosting keeps data under your control
  • Simple dashboard non-technical staff can read
Cons
  • Visitor counts are estimates
  • No long-term tracking of individual users (by design)
  • Hashed IDs are still personal data under GDPR
  • Self-hosting means updates, backups and retention are your job
  • Smaller ecosystem than Google Analytics; PostgreSQL only from v3

11. What we learned

  • Read the definitions, not just the dashboard. Our test showed "3 events", which turned out to be three clicks from repeated testing, not three people or three bookings.
  • Privacy is a spectrum. Removing cookies is a real improvement, but a hash of an IP address is still pseudonymous personal data. "Cookieless" does not automatically mean "anonymous".
  • The law moved under us. We started by framing Umami as a way to avoid consent banners; the ICO's 2026 guidance changed that argument for UK sites, so we reframed it around data minimisation.
  • Open source made checking possible. We could confirm the hashing formula and the bot filter directly in the source code instead of relying on marketing claims.
